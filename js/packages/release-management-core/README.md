# @officespacesoftware/release-management-core

Shared Git Flow primitives and workflow orchestration for release management.

This is the layer both front-ends sit on: the
[`release-management` CLI](../release-management-cli/README.md) and the
[`release-management-mcp` server](../release-management-mcp/README.md) parse inputs, call
into this package, and format what comes back. Nothing depends on either front-end, and
nothing in here imports `commander` or the MCP SDK — that is what keeps the two
interchangeable.

It orchestrates; it does not mutate versions. Every version transition goes out through
`VersionerAdapter` into [`@officespacesoftware/versioner`](../versioner/README.md), which
owns the `VERSION` file and creates the version commit and annotated tag.

TypeScript compiled to ESM (`src/` → `lib/`) with declarations. Node 18 or newer.

## Install

The package publishes to GitHub Packages, so the scope needs to be pointed there. In your
project's `.npmrc`:

```
@officespacesoftware:registry=https://npm.pkg.github.com
//npm.pkg.github.com/:_authToken=${GITHUB_TOKEN}
```

The token needs `read:packages`. Then:

```sh
npm install @officespacesoftware/release-management-core@next
pnpm add @officespacesoftware/release-management-core@next
```

The current line is a prerelease published under the `next` dist-tag. Install with `@next`,
or pin an exact version; `latest` is reserved for stable releases.

```ts
import {
  GitFlowManager,
  ReleaseAgent,
  VersionerAdapter,
  MergeConflictError,
  BranchSelectionError,
  buildChangePlan,
  renderChangePlan,
  assertPlanIsCurrent,
  StalePlanError,
} from "@officespacesoftware/release-management-core";

const gfm = new GitFlowManager(process.cwd());
const listing = await gfm.listVersions("main"); // read-only
```

`src/index.ts` re-exports six of the seven modules: `change-plan`, `git-flow`,
`release-agent`, `versioner-adapter`, `versioner-direct`, and `guards`.
`github-client.ts` is deliberately left out — see
[GitHub credentials](#github-credentials).

## `GitFlowManager`

Git and GitHub primitives, scoped to one working directory. Every method is a thin,
independently useful operation; `ReleaseAgent` composes them into workflows.

```ts
const gfm = new GitFlowManager(workingDirectory, {
  localTimeoutMs: 30_000,    // default
  networkTimeoutMs: 300_000, // default
});
```

The two timeouts are separate because a fetch or push on a large repository routinely
exceeds the local budget, and a timeout kill is indistinguishable from a real failure while
the operation may have partly completed. `isNetworkGitCommand` decides which applies.

**Status and reads**

| Method | Returns |
| --- | --- |
| `getStatus()` | `GitStatus` — current branch, cleanliness, staged/modified/untracked |
| `validateNoStagedChanges()` | throws when anything is staged |
| `isGitRepository()` | `boolean` |
| `getBranches()` | `GitBranchInfo[]`, local and remote |
| `getCurrentCommit()`, `getBranchHead(branch)` | sha |
| `getLatestTag()` | `string \| null` |
| `commitSubject(ref)`, `commitsNotIn(branch, base)` | commit subjects |
| `refExists(ref)` | `boolean` |
| `readFileFromBranch(branch, path)` | file contents at a ref |
| `readBranchVersion(ref, prefer?)` | first line of that branch's `VERSION`, or `null`; `prefer` is `"local"` (default) or `"remote"` |
| `filesChangedSinceFork(baseRef, headRef)` | `string[]` |
| `checkContentDiff(a, b)`, `checkIsAncestor(ancestor, descendant)` | `boolean` |
| `compareBranches(a, b)` | `BranchComparisonResult` — ahead, behind, synchronized, divergent |
| `verifyMainDevelopSync()` | `{ synchronized, message, canProceed }` |
| `listVersions(productionBranch?)` | `VersionListing` — every release/hotfix branch with its version, tag presence and merge status. Read-only. |

**Fetch and checkout**

`fetchBaseBranches()`, `fetchBranch(name)`, `pullBranch(name)`, `checkoutAndPull(name)`.

**Branches and tags**

`createReleaseBranch(version)`, `createMergeBranch(opts)`, `pushBranch(name)`,
`pushBranchAndTag(branch, tag)`, `tagExistsLocally(tag)`, `tagExistsRemotely(tag)`,
`deleteTagLocally(tag)`, `deleteTagRemotely(tag)`, `deleteLocalBranch(name)`,
`deleteRemoteBranch(name)`, `revertCommit(sha)`.

**Pull requests**

`createPullRequest(branch, base?, title?, body?, draft?)`,
`findOpenPullRequest(branch, base)`, `closePullRequest(number, { comment })`,
`parsePullRequestNumber(url)`,
`waitForPullRequestChecksToStart(number, { timeoutMs, pollIntervalMs })`.

Generated bodies are wrapped in `MCP_WATERMARK_START` / `MCP_WATERMARK_END`, so updating a
pull request rewrites only the generated region and leaves human edits outside it alone.
`autoGeneratedFooter()` supplies the attribution line and `productionMergeWarning(kind)`
the banner every PR into the production branch carries.

**GitHub releases**

`getGitHubRelease(tag)`, `createGitHubRelease(version, branch)`,
`deleteGitHubRelease(id)`.

**Merge analysis**

`previewMergeConflicts(baseRef, sourceRef)` uses `git merge-tree --write-tree` and touches
neither `HEAD` nor the working tree — this is the one to reach for.
`detectMergeConflicts(base, source)` does a real trial merge and therefore moves `HEAD`; it
refuses to run over tracked local changes, because its cleanup would discard them.

**Branch classification**

`detectBranchType(name)`, `getBaseBranch(type)`, `getTargetBranch(type)`,
`findBranchesOfType(type)`, `findLatestBranch(type)`, `validateBranchVersion(info)`,
`resolveDownmergeBranch(type, version?)`, `describeMainDownmerge()`.

**Downmerge execution**

`downmergeMainToDevelop()`, `downmergeReleaseToDevelop(version?)`,
`downmergeReleaseToMain(version?)`, `downmergeHotfixToDevelop(version?)`,
`downmergeHotfixToMain(version?)`. The three returning `DownmergeResult` report which
shape they took — `direct`, `merge-branch`, or `merge-branch-with-conflicts`, the last
carrying the conflicted files and the transient build-trigger PR.

`MergeConflictError` carries `conflictedFiles`.

## `ReleaseAgent`

The multi-step workflows, target-branch selection, and plan construction.

```ts
const agent = new ReleaseAgent(gfm, workingDirectory);
await agent.initialize();  // connects the versioner adapter
```

`initialize()` is required before any `execute*` call, because those mutate versions.
Planning does not need it — the MCP server builds a deliberately uninitialized agent for
read-only planning so that describing a change never requires the versioner library.

**Plan** — each returns a `ChangePlan` and changes nothing:

```
planCreateReleaseCandidate(releaseType)   planDownmergeMainToDevelop()
planCreateHotfix()                        planDownmergeReleaseToDevelop(version?)
planIncrementRC(version?)                 planDownmergeReleaseToMain(version?)
planReleaseVersion(version?)              planDownmergeHotfixToDevelop(version?)
planRevertVersion(version?)               planDownmergeHotfixToMain(version?)
```

**Execute** — each returns a workflow context recording every step:

```
executeRCWorkflow(releaseType, workingDirectory, dryRun?)   → ReleaseWorkflowContext
executeHotfixWorkflow(workingDirectory, dryRun?)            → HotfixWorkflowContext
executeIncrementRCWorkflow(workingDirectory, v?, dryRun?)   → IncrementRCWorkflowContext
executeReleaseWorkflow(workingDirectory, v?, dryRun?)       → ReleaseVersionWorkflowContext
executeRevertVersionWorkflow(workingDirectory, v?, dryRun?) → RevertVersionWorkflowContext
```

Each context carries `stepProgress: WorkflowStep[]` with a per-step status of `pending`,
`in_progress`, `completed`, `failed` or `skipped`, plus whatever the workflow produced —
`pullRequestUrl`, `releaseUrl`, `ownBasePullRequestUrl`, and for a revert the
`shape` (`"revert"` or `"abandon"`) and which tags were deleted where.
`getWorkflowContext()` returns the current one and `getProgressSummary()` renders it.

`isVersionerAvailable()` reports whether the version-mutation layer is reachable;
`cleanup()` disconnects it. `BranchSelectionError` is thrown when no branch can be chosen —
none matching, or the choice is ambiguous.

`predictIncrementedRC("1.2.3-RC.4")` → `"1.2.3-RC.5"` and
`predictPromotedVersion("1.2.3-RC.4")` → `"1.2.3"` state a pending transition before it
happens; both are exported so a front-end can name the outcome in a plan.

## Change plans

A plan describes the git objects an action would create or delete, and carries a digest of
the repository state it was computed against. Applying it later re-derives the plan and
refuses if the digest moved, rather than acting on stale intent.

```ts
const plan = await agent.planReleaseVersion();
console.log(renderChangePlan(plan));
// … later, with the digest the operator approved
assertPlanIsCurrent(await agent.planReleaseVersion(), providedDigest);
```

| Export | Purpose |
| --- | --- |
| `ChangePlan` | `action`, `targetBranch`, `targetBranchHead`, optional `currentVersion`/`resultingVersion`, `mutations`, `warnings`, `digest` |
| `PlannedMutation` | one object: `kind`, `operation`, one-line imperative `summary`, optional `detail` |
| `MutationKind` | `branch`, `commit`, `tag`, `push`, `pull-request`, `github-release` |
| `MutationOperation` | `create` or `delete`; `mutationOperation(m)` defaults an absent value to `create` |
| `buildChangePlan(input)` | computes the digest — a 12-character SHA-256 prefix over a canonical serialisation |
| `renderChangePlan(plan)` | human-readable text, grouped into "Would create" and "Would delete" |
| `assertPlanIsCurrent(plan, provided)` | throws `StalePlanError` on mismatch |
| `StalePlanError` | carries the freshly computed `.plan` so the caller can show what changed |

The digest covers the target branch's `HEAD` — so a push to that branch invalidates the
plan — and the warnings, because those encode remote facts a sha does not: whether a tag
already exists, whether a pull request will be updated rather than created.

The protocol both front-ends build on top of this is documented in
[docs/actions.md](../../../docs/actions.md#the-planconfirm-protocol).

## Guards

Reusable preconditions, each throwing with a message a front-end can surface directly:

```ts
await ensureGitRepository(gfm, workingDirectory);
await ensureNoStagedChanges(gfm);
ensureVersionerAvailable(agent);
```

## The versioner bridge

`VersionerAdapter` is the high-level interface: `initialize`, `getCurrentVersion`,
`createReleaseCandidate(type)` and its three per-type variants,
`incrementReleaseCandidate`, `releaseVersion`, `initializeProject(version?)`,
`isVersionerAvailable`, `getAvailableTools`, `disconnect`. Version-returning methods
resolve to `VersionInfo` — `{ version, isReleaseCandidate, major, minor, patch, rcNumber }`.

Underneath, `VersionerDirectClient` calls the versioner package's exported task functions
**in-process** — no subprocess, no MCP hop. Worth knowing: it `process.chdir`s into the
target working directory for the duration of each call and restores the previous cwd in a
`finally`. That makes concurrent calls against different directories unsafe within one
process.

## GitHub credentials

`createGitHubClient` resolves a token from the first non-empty of:

1. `GH_TOKEN`
2. `GITHUB_TOKEN`
3. the output of `gh auth token`
4. `~/.config/gh/hosts.yml` → `github.com.oauth_token`

Locally, `gh auth login` once is enough — step 3 picks it up. For non-interactive shells or
hosts without `gh`, set `GH_TOKEN` to a PAT with `repo` scope. `owner` and `repo` come from
`git remote get-url origin`; only `github.com` SSH and HTTPS forms parse. Clients are cached
per working directory.

REST and GraphQL both go through `@octokit`, so no `gh` binary is needed at runtime — it is
only one of four ways to find a token.

`github-client.ts` is intentionally absent from `src/index.ts`: front-ends get their GitHub
access through `GitFlowManager`, which owns the calls, rather than holding an Octokit handle
of their own. Full detail in
[docs/architecture.md](../../../docs/architecture.md#github-token-resolution-order).

## Development

From this directory:

```sh
pnpm build         # tsc — src/ to lib/ with declarations
pnpm dev           # tsc --watch
pnpm test          # node --test test/*.test.mjs, preceded by pretest: tsc
pnpm clean         # rm -rf lib/
```

The suite is fifteen files under `test/`, covering branch selection, change plans, the
creation/downmerge/version-bump/revert plan builders, merge previews, PR bodies, release
notes, version listing, and that read-only plans stay read-only. Tests run against
compiled `lib/`, which is why `pretest` builds first.

`js/packages/release-management-core/src/` is laid out as:

```
src/
├── index.ts             # barrel; six of seven modules
├── git-flow.ts          # GitFlowManager and its types
├── release-agent.ts     # ReleaseAgent: workflows and plan builders
├── change-plan.ts       # plans, digests, rendering
├── versioner-adapter.ts # high-level version mutation
├── versioner-direct.ts  # in-process versioner client
├── github-client.ts     # token resolution, Octokit handles (not exported)
├── guards.ts            # shared preconditions
└── versioner.d.ts       # ambient types for the JS versioner package
```
